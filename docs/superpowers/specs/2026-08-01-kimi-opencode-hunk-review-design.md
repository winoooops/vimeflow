# Kimi and OpenCode Hunk Review Support

**Delivery:** two sequenced pull requests. PR 1 owns the shared foundation and Kimi Code support. PR 2 adds OpenCode after PR 1 merges.

**Design source:** [`docs/technical-notes/2026-08-01-kimi-opencode-hunk-review-architecture.zh-CN.html`](../../technical-notes/2026-08-01-kimi-opencode-hunk-review-architecture.zh-CN.html)

## 1. Scope and Architecture Decision

The feature extends hunk comments, structured replies, and delegated reviews from Claude Code and Codex to Kimi Code and OpenCode. PR 1 delivers the shared foundation plus complete Kimi support; PR 2 adds OpenCode after PR 1 merges.

Each adapter owns only the provider-specific boundary: determining when its native transcript contains one complete assistant turn and reproducing that turn's reviewer text. Shared code owns sentinel selection, schema validation, normalized `agent-reply` / `agent-review` events, nonce-scoped recovery, and frontend ingestion.

The implementation extends the existing `TranscriptStreamer` live/recovery contract and shared extractors. It does not add another `BaseAdapter`, provider-specific IPC/events, a universal completed-turn DTO, or agent-name-based feature routing.

A provider may set `supportsHunkReview: true` only after dispatch, live reply, reply recovery, live review, review recovery, replay suppression, and hunk ingestion are covered.

Non-goals include a breaking OpenCode bridge schema-version change or database migration, rewriting Claude/Codex adapters, or duplicating provider-neutral frontend tests. PR 2 may add an optional field to a version-1 bridge record when old rows decode fail-closed.

## 2. Shared Protocol and Base Recovery Contract

`reply.rs` and `review.rs` remain the only owners of sentinel parsing, schema validation, malformed degradation, and event mapping. A marker is recognized only when it occupies a standalone line after optional whitespace and one block-quote prefix are removed; marker literals inside JSON strings or prose are data. Both protocols select the last complete line-delimited block, and a trailing orphan open marker cannot shadow an earlier complete block. When no complete block exists, the last orphan open marker retains the current malformed best-effort behavior. The existing reply implementation is tightened into this shared selector and reused by review rather than introducing another parser module. Before either extractor runs, one shared arbitration check counts standalone protocol open markers in the completed turn: if both `VIMEFLOW_REPLY` and `VIMEFLOW_REVIEW` are present, the turn is nonconforming and emits neither event. A turn containing repeated markers for only one protocol continues through that protocol's existing last-complete-block rule.

`TranscriptStreamer` remains the central adapter interface. Its default `recover_replies` and `recover_reviews` implementations return empty results, while capable providers override them. The recovery methods receive the session ID, requested nonces, and an ordered slice of `RecoveryPath { original_path, canonical_identity }` records. The canonical identity returned by validation is the path used to start the live tailer and later group aliases after revalidation; the original provider path is retained specifically so recovery can revalidate it and perform the later no-follow open without opening the resolved target. A default-empty `recovery_paths()` hook lets a provider expose additional records that it validated and successfully tailed internally. A second default, `recovery_domain() -> Option<RecoveryDomain>`, returns `None` so adapters that do not explicitly identify their trust boundary never inherit history. A concrete domain is only `{ agent_type, canonical_validator_trust_root }`; it is provenance for path reuse, not a new completed-turn abstraction. Every adapter freezes one canonical validator root at construction/attach and uses that same value for validation and domain identity; it may not recompute the root during recovery. Claude Code and Codex freeze the roots their current validators use, while Kimi and OpenCode freeze their locator-backed effective roots. One base `merge_recovery_paths` operation deduplicates exact `original_path` values by last occurrence: seeing an existing original removes its old record and appends the newest validated record, while distinct originals are preserved even when their current canonical identities match. The operation then retains the newest `MAX_RECOVERY_PATHS = 256` records and performs no filesystem I/O.

Immediately before every recovery read, the current provider revalidates `original_path`; the returned canonical target must remain under the frozen root and replaces the record's canonical identity for that scan. Every `ValidateTranscriptError` variant (`NotFound`, `OutsideRoot`, `InvalidPath`, `NotAFile`, or `Other`) skips only that candidate; validation cannot prove it remains a trusted readable transcript. Revalidated records are grouped by canonical identity without discarding aliases. Each group tries original paths from newest to oldest through the promoted existing `filesystem::scope::open_nofollow` primitive, never opening the resolved target; `NotFound` or `Symlink` skips that alias and tries the next, every other I/O error aborts recovery, and the first successful alias is scanned exactly once. Thus paths that converge on one target cannot duplicate turns, while a newest symlink alias cannot hide an older readable regular path. The original 256-record bound applies before grouping, so fallback remains bounded. Existing filesystem callers format the typed error at their boundary. Deleted paths, paths resolving outside the trust root, and groups with no readable no-follow alias are skipped before bytes are consumed. This matches the existing provider transcript-reader threat boundary; it does not claim to defeat a compromised same-user process that repeatedly swaps parent path components between separate validation/open syscalls. Closing that repository-wide limitation requires fd-relative, component-by-component no-follow traversal and is outside these two feature PRs. Recovery still never accepts a renderer-supplied path.

Retained records are numbered oldest-to-newest before revalidation. A canonical group's `path_ordinal` is the ordinal of its newest member, groups are traversed by that ordinal ascending, and every completed turn read through a fallback alias uses the group ordinal rather than the chosen alias's position. Alias fallback therefore cannot change equal/missing-timestamp order or first-review selection.

All agent publication, replacement, recovery-source, and generation-close operations use the same existing `TranscriptState::session_gate(session_id)`; there is no second agent gate. The transcript-hint flow retains the provider's pre-validation path, then passes `RecoveryPath { original_path, canonical_identity }` from the successful validator into `TranscriptState::start_or_replace`; the canonical identity is used to start the current tailer, while the full record is registered for later revalidation and no-follow recovery open. Every `AgentBindings::for_attach` call receives a process-local monotonic `attach_instance_id`, shared by that attach's watcher and streamer. The `AlreadyRunning` predicate requires equal `pty_generation`, `attach_instance_id`, canonical transcript path, and cwd, plus recovery domains that are both `Some` and equal; `None` never matches, including `None` against `None`. Repeated notify/poll work for one attach may return `AlreadyRunning`, while a new provider process attached to the same PTY/path/cwd always replaces the old source. A new PTY generation, provider switch, validator-root change, or default-domain adapter likewise cannot silently rebind old state.

Replacement is a two-gate-phase operation around blocking work. Under the session gate it rechecks identity/generation/attach ID, assigns a monotonically increasing replacement token/source revision, creates a one-shot installation latch, marks the entry `Replacing { token, latch }`, detaches the old live handle, and signals its stop flags. It then releases the gate, joins the old tailer, snapshots `recovery_paths()` from the quiescent old streamer, and starts the new tailer. A concurrent callback observing the same replacement identity returns `AlreadyRunning`; a different identity observes `Replacing` and retries through the existing watcher notify/poll path rather than starting another replacement. Recovery observing `Replacing` clones the latch, releases the session gate, waits for `Installed` or `Aborted`, then reacquires and retries source lookup; it never scans an uninstalled source and never waits while holding the gate. `TranscriptStreamer::tail` must return its handle before emitting any event synchronously. The newly spawned worker receives an attach-scoped sink carrying the installation latch; before its first event it waits outside the gate, then forwards only after `Installed` and the normal identity check. PR 1 moves both Kimi's and OpenCode's current synchronous initial cwd emission into their workers as shared-latch compatibility work; no startup caller waits on its own latch, while OpenCode hunk-review parsing remains PR 2. The operation reacquires the session gate and installs only if its token, generation, and attach ID are still current, then sets `Installed` and notifies all waiters. If any identity no longer matches, it sets `Aborted`, notifies, and signals/joins the uninstalled new handle outside the gate. On successful installation, old base history and the old streamer snapshot are merged with the new registered `RecoveryPath` only when both streamers return the same non-`None` `RecoveryDomain`. A provider switch, validator-root change, or either `None` domain discards inherited paths and installs only paths validated for the new source. If new tail start fails, the token holder reacquires the gate and restores the stopped old streamer/history only when the old source belongs to the same current attach tuple and has the same non-`None` domain; otherwise it leaves recovery empty. It then sets `Installed` for a restored source or `Aborted` for no source and notifies. Permanent generation or attach replacement always sets `Aborted` and notifies. No latch wait, tailer join, or provider filesystem I/O occurs while the session gate is held.

Normatively, the `Replacing` entry retains `{ token, latch, pty_generation, attach_instance_id, canonical_path, cwd, recovery_domain, old_recovery_source }`; callbacks compare the full stored identity, and install/restore checks use those stored values rather than recomputing them after gate release.

Both recovery entry points acquire the session gate. An installed entry is usable only when its `(pty_generation, attach_instance_id)` equals the current watcher tuple and its domain is `Some`; recovery clones that tuple with paths, domain, and revision before releasing the gate for scanning. A `Replacing` entry follows the latch/retry rule above. After scanning, recovery reacquires the gate and returns events only if the currently installed source has the same revision, generation, attach ID, and domain, the tuple is still current, and the generation is not closed; otherwise it discards stale results. A replay summary emitted by a newly started tailer waits on the same installation latch, while replacement or teardown during I/O cannot leak old events under a reused session ID. No lifecycle/session gate is held across a latch wait or recovery filesystem I/O.

The current streamer and history survive a normal live-tail stop. Each PTY spawn receives a monotonically increasing process-local `pty_generation`, which is stored with the managed session. `PtyState` adds one short process-local lifecycle mutex shared by session insertion, attach snapshotting, explicit close, and terminal finalization; the intentionally global gate keeps the implementation small, and these operations are too infrequent to justify a per-session lock registry. `attach_snapshot(session_id)` acquires lifecycle then sessions, and returns generation, cwd, shell PID, and PTY start time from one managed-session snapshot before releasing both; `resolve_bind_inputs` uses only that snapshot plus provider detection derived from its shell PID, so it never combines A facts with B's generation. `AgentBindings::for_attach` receives the snapshot generation and a process-local monotonic `attach_instance_id`. During `BackendState` construction, `PtyState` receives one generation-removal callback that captures cloned `AgentWatcherState` and `TranscriptState`; this is the only terminal-to-agent lifecycle seam. Reader/reaper finalization supplies its expected generation, acquires lifecycle then sessions, and removes the entry only when that generation matches. Immediately after releasing the sessions mutex but before any cache mutation or terminal event, a successful finalization invokes the callback while still holding lifecycle. The callback acquires the one `TranscriptState` session gate, atomically closes that exact generation, marks and detaches the matching watcher, removes the matching transcript/recovery source and history, aborts/notifies any `Replacing` latch, signals stop flags, and returns the detached handles without dropping them. Finalization then applies its exited/error cache mutation and publishes its generationless `pty-exit`/`pty-error`, releases lifecycle, and only afterward drops/joins the returned handles and performs bridge cleanup. The implementation uses one small concrete teardown return value for the existing watcher/transcript handles, not another provider abstraction. A generation mismatch is a complete no-op. Explicit user close acquires lifecycle before looking up the current PTY and captures its generation. It calls the existing child kill against that exact managed session while lifecycle prevents ID reuse; `KillFailed` releases the gate, returns the existing error, and preserves PTY, cache, generation, and agent state for retry. On kill success it removes only the captured generation, performs the same nonblocking generation close, and deletes the cache entry before releasing lifecycle; when no PTY exists because EOF already finalized it, close only deletes the exited cache entry. Reader-owned EOF, read-error, and ephemeral-reap paths pass their captured generation, so a delayed handler for generation A cannot affect replacement generation B whether B existed before finalization or attempts insertion during it. Both `AgentWatcherState` registration and `TranscriptState::start_or_replace` acquire the one session gate and reject a closed generation before publication, including an attach with no valid transcript hint; an A snapshot that finishes detection after teardown is rejected under that same gate, while a later B snapshot can attach normally. One attach-scoped `GenerationEventSink` wraps the existing sink passed only to agent watchers/tailers. Its `emit_json` first waits on any replacement installation latch outside the session gate, then acquires the gate and forwards `agent-status`, `agent-reply`, `agent-review`, and other agent events only after `Installed` and while its captured generation is not closed; `Aborted` or closed returns success without emitting. The close operation and event forwarding are therefore ordered under one gate: an A emit already inside the gate completes before A closes and before B can insert, while an A worker arriving afterward is discarded even if its handle has not joined. Terminal events keep the original sink, and no event schema changes. The fixed lock order is lifecycle gate → PTY sessions mutex (released before callback) → `TranscriptState` session gate; agent attach/replacement/event paths never acquire lifecycle while holding the session gate. No latch wait or blocking join occurs under either gate. A provider may add a concrete path only through its existing trusted locator and transcript validator; it may never open a renderer-supplied or unvalidated path.

After a successful kill, a cache mutation closure failure cannot resurrect the already-terminated PTY or agent state: close releases lifecycle and returns that cache error, leaving the pre-mutation cache entry for an idempotent close retry. Until retry, the existing `list_sessions` reconciliation observes no PTY and marks the entry exited, so it is never presented as live. A disk flush failure remains the existing best-effort case: `SessionCache::mutate` has already deleted the in-memory entry, logs the flush error, and returns success; a later mutation or graceful shutdown retries persistence, while next-start reconciliation treats any stale disk row as exited.

The event predicate is the exact tuple `(pty_generation, attach_instance_id)`, not generation alone. Watch startup is reordered into prepare → commit → activate. `prepare_watch` completes every fallible OS watcher/setup step but neither runs inline decode/tail work nor enables callbacks. Under the session gate, `AgentWatcherState::insert_prepared` rechecks the open generation and accepts a candidate only when no attach is committed for that generation or its process-monotonic `attach_instance_id` is greater than the committed ID; an equal or lower ID is stale and the prepared watcher is dropped without mutation. A successful commit atomically installs the prepared watcher plus its current attach ID. A new attach instance never inherits recovery: the commit detaches and signals any old watcher/live transcript handle, aborts its replacement latch, clears its recovery source/history, and returns those handles for join after releasing the gate. This applies even when provider/domain matches and when the new attach has no transcript hint; only path replacement inside one attach can inherit history. After the returned old handles are joined outside the gate, `activate_registered` enables notify/poll and runs the initial decode/tail through callbacks that recheck the tuple; ordinary missing/invalid initial input remains retryable instead of making activation transactional. A preparation failure leaves the old watcher/transcript untouched, and a prepared attach superseded before commit is dropped without running transcript work. A new attach in the same PTY changes the current ID only at successful commit, and exact-generation teardown clears it only when still matched. Every attach-scoped sink, recovery entry point, and `start_or_replace` checks both values while holding the gate, so initial events forward and late work/history from an older process is suppressed after the new watcher commit.

Here, watcher “drop” under the gate is only logical rejection or detachment. Before an installed or prepared watcher leaves guarded state, the code marks it stale, sets its existing `owns_transcript` cascade to false, extracts it from state, and returns it to the caller together with any separately detached transcript handle. Stop flags may be signalled under the gate, but no watcher/transcript destructor, thread join, or callback-producing cleanup runs there. The caller releases the gate before dropping or joining every returned handle. Transcript removal is performed explicitly while the gate still has the exact generation/attach tuple, never later through a detached watcher's `Drop`. An equal/lower-ID prepared candidate follows the same return-for-outside-cleanup path even though it was never activated. Consequently, an old handle dropped after a newer same-session attach commits cannot call `TranscriptState::stop(session_id)` and remove the newer source.

The installation latch belongs only to recovery waiters and the candidate tailer's attach-scoped sink. An incumbent watcher/tailer retains its original installed sink; after the gate marks the source `Replacing`, an incumbent event that fails the stored identity/revision predicate is discarded immediately and never waits on the candidate's latch. Only the newly started candidate worker receives that latch and waits for `Installed` before its first event. Replacement can therefore join the incumbent outside the gate without the incumbent waiting on a decision that itself depends on that join.

The renderer supplies only session ID and requested nonces. It never supplies a transcript path. Recovery work is bounded per call: the shared tail-line reader scans at most `MAX_RECOVERY_BYTES_PER_PATH = 128 * 1024` of payload from the tail of each of at most 256 retained paths, for a 32 MiB payload ceiling plus at most 256 one-byte boundary probes. Every retained path receives its own window, so a large current file cannot consume the older paths' budget. A file read from byte zero keeps its first line. For a nonzero seek offset, the reader inspects the preceding byte and discards the first window line only when that byte is not `\n`, meaning the window truly begins mid-line. The existing per-line byte cap remains. Recovery guarantees only turns inside each path's documented tail window. Provider-native reconstruction retains only the newest `MAX_RECOVERY_COMPLETED_TURNS = 512` completed texts by a total native completion key before sorting that fixed window chronologically. Claude Code and Codex parse their RFC 3339 top-level `timestamp`; Kimi uses the epoch-millisecond top-level `time` on the JSONL record carrying `step.end`; OpenCode uses the bridge row's epoch-millisecond `ts`. The key is `(has_valid_timestamp, timestamp, path_ordinal, line_ordinal)`: invalid/missing timestamps sort older than every valid timestamp and are evicted first; equal values use the stable path/line suffix without claiming stronger chronology. Two small base collectors pass the ordered texts through the shared extractors. Reply recovery considers every requested-nonce match in the retained window because delegated-review follow-up turns reuse the original review nonce, but retains only the newest `MAX_RECOVERED_REPLY_EVENTS = 128` matches and returns that window in original order. With no stable turn ID, content-identical outcomes collapse in existing frontend ingestion while different payloads remain ordered. Review recovery consumes a nonce after its first matching completed review, yielding at most the existing 50 requested nonces, because an initial delegated review is one-shot and `useAgentReview` clears that pending request. Provider read errors propagate through the existing IPC error path.

Both shared protocols enforce a 24 KiB sentinel-payload limit before trimming or block-quote normalization and a `MAX_SENTINEL_MARKER_LINE_BYTES = 256` limit on each raw marker line including indentation, optional block-quote prefix, trailing whitespace, `\r`, and `\n`; an over-limit line is not a marker. Marker recognition first records byte ranges in the original completed-turn UTF-8. For a complete block, the measured slice starts immediately after the opening marker line's `\n` (or at EOF if it has none) and ends at the first byte of the closing marker line; it therefore contains only raw lines strictly between the marker lines, with each payload line's original `\n` and any preceding `\r` counted. Marker-line bytes are excluded from the payload count, but their separate 256-byte caps keep a conforming structured suffix at most 24.5 KiB. Adjacent marker lines have a zero-byte payload. For a lone orphan, the slice uses the same start and extends to the completed turn's EOF. Shared extractors also receive one `starts_at_line_boundary` boolean, defaulting to `true` for complete untruncated turns. A bounded live buffer records whether its retained first byte was originally at turn start or immediately after `\n`; UTF-8 clamping updates this provenance from the byte preceding the chosen code-point boundary. When false, marker recognition skips the retained first partial line, so clamping immediately before an originally inline marker cannot manufacture a standalone marker. This is a boolean parameter/state on existing extractors and provider-private buffers, not a completed-turn DTO. A conforming assistant turn contains at most one structured block: a feedback/follow-up dispatch requests `VIMEFLOW_REPLY`, while a delegated-review dispatch requests `VIMEFLOW_REVIEW`. Dispatch prompts require that raw slice and marker lines fit their limits and remain at the end of the turn, so the 32 KiB provider tail buffers retain the complete block plus its markers and its true line-boundary provenance. A complete or orphan over-limit block is malformed when the provider still supplies it in full. Oversized payloads are never partially parsed as JSON: reply emits `nonce = None` and a diagnostic truncation notice plus UTF-8-safe raw tail whose total is at most 24 KiB; review emits `nonce = None`, `reviewer = None`, and no findings. Frontend ingestion cannot safely correlate either nonce-less event and therefore ignores it immediately. The existing persisted `dispatchedAt` fields instead drive one provider-neutral `MAX_PENDING_AGENT_RESPONSE_AGE_MS = 30 * 60 * 1000` expiry: mount/restore, each active-PTY recovery cycle, and one timer for the earliest pending deadline prune expired feedback and delegated-review requests. Feedback expiry attaches a plain failure note to the lowest pending handle; delegated-review expiry adds a review-level note. Both messages say that no valid structured response arrived within 30 minutes and that an oversized or malformed response may be the cause, then clear the persisted pending record so reload cannot retry forever. This uses existing stores, notes, and timers rather than a new event or provider-specific notification path. Best-effort metadata recovery remains only for malformed payloads within the size limit, where the complete bounded JSON text is available. Tail-clamped providers make no recovery guarantee for invalid output larger than their 32 KiB turn bound; they remain memory-bounded and must not emit a structured event from a truncated fragment.

Live capture and recovery must call the same shared extractors. They may differ only in event delivery: live emits through `EventSink`; recovery returns normalized event vectors.

No new `AgentAdapter` façade methods, IPC commands, event types, parser dependencies, or generic completed-turn DTO/trait are introduced. `recovery_paths()` and fail-closed `recovery_domain()` are narrow hooks on the already central `TranscriptStreamer`; the base collectors are functions over an iterator of completed text, not another provider abstraction.

## 3. Provider Completed-Turn Contracts

### Kimi Code — PR 1

Kimi does not expose one record containing a complete assistant message. The existing 32 KiB UTF-8-safe tail buffer is factored into a small Kimi-private accumulator shared by the live decoder and recovery scanner:

- Only the main agent `wire.jsonl` contributes content.
- A real user prompt starts a new turn and clears any unfinished buffer.
- Only text `content.part` records are appended; thinking, subagent, and tool content are excluded.
- Only a main-agent `step.end` with `finish_reason == end_turn` produces complete reviewer text.
- Replay advances the same accumulator state but suppresses only live `agent-reply` and `agent-review` emission; existing lifecycle, activity, and replay-summary behavior is unchanged.
- The completed text is checked by both shared extractors, while the dispatch contract allows at most one protocol block in a conforming turn.

The accumulator carries the shared `starts_at_line_boundary` provenance alongside its text and updates it on every tail clamp; it does not normalize or insert newlines.

Kimi `tail()` spawns and returns its handle before the worker emits the initial `agent-cwd`; that worker emission passes through the replacement installation latch and attach tuple predicate.

Each per-attach `KimiAdapter` freezes the canonical `KimiLocator::effective_home()` while the process context is available, before its first validation/tail, and uses that stored `recovery_root` for both `RecoveryDomain` and every later validation. Process exit or `/proc` disappearance therefore cannot switch recovery to a fallback home. The adapter applies `merge_recovery_paths` to the main wires its supervisor successfully tailed and exposes that bounded snapshot through `recovery_paths()`. `TranscriptState` captures the snapshot after the old supervisor stops, so the next adapter receives old supervisor-discovered wires through base history without global Kimi state or a cleanup hook. Recovery uses the merge operation only to bound base history, its current local set, and a newly refreshed validated candidate to 256 records; after revalidation it preserves converging aliases and delegates canonical grouping plus newest-to-oldest no-follow fallback to the shared recovery reader. Locator discovery alone never enters either trusted set. Kimi revalidates every retained original path against its frozen root immediately before the shared no-follow group open; the returned canonical path is identity only and is never opened. It scans the 128 KiB tail window of the first readable alias in every accepted canonical group. Each path scanner starts in `awaiting_user_prompt`; it ignores leading `content.part` and `step.end` records until it observes a real main-agent user prompt, because the tail window may begin in the middle of a turn even when its first retained JSONL record is complete. After that prompt it applies the normal accumulator rules, with every later prompt clearing an unfinished turn. This intentionally drops a leading turn whose prompt fell outside the recovery window rather than manufacturing a standalone marker from partial context. The scanner keeps the newest 512 provider-private completed texts in a fixed-size completion-key heap, then sorts that bounded window by the enclosing `step.end` record's top-level epoch-millisecond `time` plus stable path/line tie-breakers before calling the base collectors. A normal A → B → A sequence with distinct timestamps is restored chronologically; equal or missing timestamps have only deterministic tie order. A successful current-wire scan does not prevent scanning an earlier retained target, although only turns inside each target's tail window are guaranteed. Any `ValidateTranscriptError` skips that candidate; `OpenNoFollowError::NotFound` or `OpenNoFollowError::Symlink` tries the next alias in its group; every other open error and any read error terminate recovery immediately. Kimi never reads subagent wires or accepts a renderer-supplied path.

### OpenCode — PR 2

The OpenCode bridge already emits one complete `assistant.text` record when the session becomes idle, but its current JavaScript clamp counts UTF-16 code units and can split an astral character. PR 2 replaces the three independent session maps with one bounded `Map<sessionID, SessionState>`, `MAX_TRACKED_SESSIONS = 64`, that also owns `lastDirectory`, an active-turn flag, and an LRU ordinal. Only `session.created` admits a new session; message, part, updated, idle, and error events for an unknown ID never allocate state. When creation arrives at capacity, the bridge evicts the oldest inactive entry. If all 64 entries have active turns, that creation and all subsequent unknown-ID suffix events are ignored, so a partial turn cannot be reconstructed after a slot later becomes free. `session.idle` and a scoped `session.error` clear turn buffers and mark the retained entry inactive, making completed sessions reclaimable without a lifetime quota. Before any lookup or insertion, the session ID must pass the existing `sessionFilename` contract (non-empty, at most 128 characters, and `SAFE_SESSION_ID`); `MAX_BRIDGE_ID_BYTES = 256` applies separately to message and part IDs. A session-info directory is stored and indexed in full only when its UTF-8 length is at most `MAX_DIRECTORY_BYTES = 2 * 1024`. On an over-limit directory transition, the bridge clears the session's routable directory and appends one index row with `directory: ""`. PR 2 updates the locator to collapse index history to the newest row per session before cwd matching and makes `resolved_directory_for` return `None` for an empty directory, so that invalidation row shadows every older cwd. Repeated oversized updates do not append duplicate invalidation rows, while a later valid directory appends the exact new value.

Each `SessionState` separates role-unknown tolerance from confirmed assistant capture. One bounded message index tracks at most `MAX_TRACKED_MESSAGE_IDS = 256` IDs and their known role; `pendingMessages` is an LRU of unknown-role accumulators within that same ID limit and an aggregate `MAX_PENDING_TEXT_BYTES = 64 * 1024` budget. A pending accumulator uses the exact confirmed accumulator rules for active part ID, full-snapshot replacement, committing on the next part ID, UTF-8 tail clamping, and line-boundary provenance, so one accumulator can retain at most 32 KiB committed plus 32 KiB active. Promotion moves a retained accumulator without rejoining or duplicating snapshots. Before an insert or update would exceed the aggregate pending budget, the bridge evicts the oldest whole pending accumulators and marks those message IDs ignored for the rest of the turn; an evicted accumulator is never partially retained or later promoted. A new ID beyond 256 is likewise ignored for the current turn; neither condition marks the confirmed assistant turn overflowed. Updating an existing retained pending ID or part refreshes it. When `message.updated` arrives, the first valid role is stored: user discards pending text and causes later parts for that ID to be ignored; assistant promotes retained pending text exactly, or creates an empty current accumulator when role arrives before parts, and replaces any prior assistant candidate. If an ID ignored because of either resource limit is later confirmed as assistant, the bridge clears any current older assistant candidate and keeps the new ID ignored, so idle emits no superseded response; confirmation as user leaves the current candidate unchanged. Repeated updates with the same role are idempotent; a conflicting role invalidates and ignores that message for the rest of the turn.

The current assistant accumulator stores its owning `message_id`. It does not keep a map entry per text part: it holds a UTF-8 tail-clamped committed buffer of at most `MAX_REPLY_TEXT_BYTES = 32 * 1024`, plus only the active part ID and its independently tail-clamped latest full snapshot of at most 32 KiB. An update to the active ID replaces that snapshot, including a shorter snapshot, while the first snapshot of the next ID commits the prior snapshot and reclamps the committed buffer. Committed part snapshots are concatenated byte-for-byte with no inserted separator, matching OpenCode's ordered message-content array; final emission concatenates committed plus active and tail-clamps once more. This relies on OpenCode's native contract that snapshots for one text part are contiguous; the bridge does not add a seen-part set for impossible A → B → A streams. For `message.part.updated`, `part.sessionID` is authoritative; when `properties.sessionID` is also present it must equal `part.sessionID`, otherwise the event is ignored. The authoritative ID passes the same session validation before any lookup. A text part then routes by message ID and stored role: only the selected current assistant ID appends/replaces, superseded assistant IDs and known user/invalid IDs are ignored, and unknown role enters pending. If the selected ID later receives a conflicting role, its accumulator is cleared and that message is invalid for the turn. At `session.idle`, the bridge emits only the current confirmed assistant accumulator. Thus unresolved, user, or superseded assistant content cannot consume its budget, while an end-positioned block of at most 24 KiB survives when one target string is divided among more than 256 sequential text parts at Unicode code-point boundaries. Idle then clears roles/pending/current turn buffers. A `session.error` carrying a valid session ID clears only that session's turn buffers; a missing or invalid ID clears turn buffers for all at most 64 tracked sessions. Neither form emits, and both preserve `lastDirectory`. Retained text payload is bounded at 128 KiB per session: 32 KiB current committed, 32 KiB current active, and 64 KiB aggregate pending, plus bounded IDs/metadata; temporary JavaScript strings created while concatenating and reclamping are not included in that retained-state bound.

Committed, active, pending, and final combined tails carry `starts_at_line_boundary`. When a final clamp chooses its first retained byte, provenance comes from the segment that owns that byte: a cut inside a segment inspects that segment's preceding retained byte, while a cut exactly at an already-clamped segment start reuses that segment's saved provenance rather than the previous segment's trailing byte. No part boundary is treated as a line boundary unless the owning segment's saved provenance says its original adjacent text byte was `\n`. Every emitted `assistant.text` row carries this result as `data.startsAtLineBoundary`. Rust decodes the field as optional with a false default and passes it to both extractors; an older row without the field therefore skips its first retained line and cannot manufacture a marker. This additive, backward-compatible record-shape change keeps JSONL schema version 1.

PR 1 also freezes OpenCode's locator-backed canonical root, returns its concrete `RecoveryDomain`, and changes `tail()` to return its handle before its worker emits the initial `agent-cwd`. These are required compatibility changes for the shared identity/latch foundation; OpenCode reply/review parsing, recovery scanning, bridge v4, and capability opt-in remain PR 2.

The bridge installation version moves from 3 to 4. The installer compares the full existing file bytes with the embedded v4 asset and rewrites every mismatch, including a same-header truncated or modified file; the header remains informational, not the up-to-date predicate. Unix retains the existing temp-file flush plus atomic rename. Windows retains the existing temp-file plus remove/rename best effort, whose crash window may temporarily leave no plugin; the next startup's full-byte verification repairs that state. `BackendState` runs the installer during construction before PTY sessions can be created, then sets immutable run-scoped `opencode_bridge_v4_ready: bool` only after the resulting file fully matches, so a same-header corrupt file repaired during startup becomes ready in that same run. Production `BackendState::new` delegates to a `#[doc(hidden)] pub BackendState::new_with_opencode_plugins_dir(...)` constructor using `opencode_plugins_dir()`. Crate-external integration tests call that constructor with a caller-owned `TempDir`, and `BackendState::with_fake_sink` also requires an explicit caller-owned plugin directory; no test constructor defaults to the production resolver. This avoids process-global environment mutation and writes to the user's real directory while keeping the test seam on existing constructors rather than adding runtime configuration. `AttachContext` copies readiness into `AgentBindings::for_attach`; the OpenCode arm returns fail-closed when it is false. Other agents and terminals remain available, and no OpenCode live agent status means the existing picker cannot dispatch hunk review. If startup installation fails, this run performs no attach-time repair and remains fail-closed; the next backend startup retries the same installation flow. A successful startup result guarantees only that the verified v4 file is installed before subsequent process creation; no runtime plugin-load handshake is added. The JSONL schema remains version 1 and database behavior is unchanged.

After replay completes, the Rust adapter runs both shared extractors against each `assistant.text` record. Recovery uses the Section 2 total native completion key for every retained record: valid bridge `ts` first, then stable path/line ordinals; missing or invalid timestamps sort older than valid timestamps. It does not separately promise JSONL line order when a path contains decreasing timestamps. The adapter passes that single deterministic order to the appropriate base collector: reply recovery forwards requested matches within its bounded window, while review recovery keeps the first matching review per nonce.

### Architecture Boundary

No cross-provider `CompletedTurn` trait, DTO, or factory is added. Shared code consumes complete text; Claude Code, Codex, Kimi Code, and OpenCode remain responsible for producing that text according to their native transcript semantics.

## 4. Capability-Driven Frontend Routing

`AgentDef` gains an optional `supportsHunkReview?: true` capability. Support is fail-closed: a shared registry helper resolves an agent type, upcasts the selected registry entry to `AgentDef`, and returns `agent.supportsHunkReview ?? false`. The explicit upcast is required because `AGENTS` retains its narrow `as const satisfies` union and entries that omit the optional property do not otherwise expose it. Only agents with the complete dispatch, live capture, recovery, and ingestion chain explicitly opt in.

PR 1 marks Claude Code, Codex, and Kimi Code as supported. OpenCode and Shell omit the field. PR 2 adds the OpenCode flag only when its complete chain is delivered. A newly registered agent therefore remains unavailable for hunk review until its implementation explicitly opts in.

`PaneCandidate` carries the resolved boolean capability. `resolveCandidatePanes` filters by that field, matching cwd, and live status; the `SupportedAgent` string union, supported-name array, and display-name comparison are removed.

`WorkspaceView` uses the existing `agentTypeToRegistryKey` mapping to obtain the agent definition. It derives `agentLabel` from the registry display name and the capability from the shared fail-closed helper. Agent names remain presentation data and never decide feature availability, so renaming Codex CLI, Kimi Code, or a future agent cannot change dispatch behavior.

## 6. Delivery, Verification, and Rollback

PR 1 is developed in its own worktree and feature branch. It contains the shared recovery/lifecycle foundation, shared and legacy-provider regression coverage, capability-driven frontend routing, and the complete Kimi live/recovery chain. Claude Code, Codex, and Kimi opt into `supportsHunkReview`; OpenCode and Shell omit the capability. OpenCode changes in PR 1 are limited to the shared-foundation compatibility required before PR 2: freezing its locator-backed root, returning a concrete recovery domain, and moving its existing initial cwd emission into the worker. It gains no reply/review parsing, recovery collector wiring, bridge v4 change, or capability opt-in.

PR 2 starts from `main` only after PR 1 is squash-merged. It contains the OpenCode bridge v4 producer changes, provenance field, Rust live/recovery consumption, provider tests, and the final OpenCode capability opt-in. Keeping PR 2 based on the merged foundation prevents duplicated shared work and makes it independently revertible.

Each PR must pass `cargo test -p vimeflow`, `npm test -- --run`, `npm run lint`, `npm run type-check`, and `npm run generate:bindings`; any generated-binding diff must be intentional and reviewed. PR 1 manual acceptance dispatches both a hunk feedback comment and a delegated review to Kimi, verifies the reply/review lands on the correct hunk, reloads the workspace to exercise nonce recovery, and repeats a smoke regression with Claude Code and Codex. PR 2 repeats the same OpenCode flow and verifies startup repair/readiness using the v4 bridge. A provider's capability is enabled only after its full automated and manual chain passes.

The optional capability is the immediate fail-closed rollback switch: removing a provider's `supportsHunkReview` opt-in hides it from hunk-review dispatch without disabling its normal terminal or agent-status behavior. PR 2 can be reverted without reverting PR 1. Neither PR performs a database migration or breaking event/schema-version change. PR 1 and PR 2 are squash-merged so each contributes exactly one commit to `main`; OpenCode hunk-review feature work never enters the Kimi PR, while the explicitly listed shared-foundation compatibility changes do.
